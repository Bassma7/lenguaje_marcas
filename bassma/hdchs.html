Resumen: Control de versiones

Resumen: Fundamentos de los sistemas de control de versiones

1. Conceptos básicos

  • Control de versiones: registro del histórico de todos los cambios de los ficheros de un proyecto. Permite volver a versiones anteriores y trabajar en equipo.
  • Versión: el estado de todos los ficheros del proyecto en un momento concreto.
  • Repositorio: espacio donde se guarda todo el proyecto (versión actual e historial). Suele ser un directorio.
  • Historial de cambios: lista de todas las versiones guardadas a lo largo de la vida del proyecto.
  • Ventajas: trabajo colaborativo y simultáneo sin pisarse, un sitio central para el código y su historial, y espacios separados para cada versión.

2. Tipos de sistemas

  • Centralizado (SVN): un único repositorio en un servidor. Cada desarrollador tiene una copia de trabajo (working copy) y usa update (traer cambios) y commit (subir cambios). Depende del servidor: sin conexión no se puede confirmar cambios.
  • Distribuido (Git): cada desarrollador tiene una copia completa del repositorio con todo el historial. Puede trabajar sin conexión y sincronizar después. Git lo creó Linus Torvalds en 2005.

3. Repositorios local y remoto

  • Local: en tu PC. Ahí se guardan tus commits.
  • Remoto: en un servidor, en una red privada o en la nube (GitHub, GitLab, Bitbucket).
  • Push: local → remoto. Pull y fetch: remoto → local.

4. Áreas de Git y flujo de un cambio

Workspace (directorio de trabajo) → Staging area → Repositorio local → Repositorio remoto

  • Staging area (área de preparación): zona intermedia donde eliges qué cambios irán en el siguiente commit. Se llena con git add.
  • Analogía de la tienda online: add es meter productos en el carrito (y restore --staged los saca), y commit es confirmar la compra.
  • git add guarda una foto del fichero en ese momento. Si lo modificas después, hay que volver a hacer add.
  • git add no sube nada al remoto.

5. Instalación y configuración

  • Instalar Git (en Windows desde git-scm.com; en Ubuntu con sudo apt update y sudo apt-get install git).
  • Comprobar la versión: git --version.
  • Identificarte: git config --global user.name "Tu Nombre" y git config --global user.email "tu@email.com".
  • Token de acceso personal (PAT): GitHub lo usa en lugar de la contraseña. Se crea en Settings → Developer settings → Personal access tokens. Para consola, permisos repo (y workflow si usas GitHub Actions). Se puede revocar o regenerar.
  • Guardar el token: git config --global credential.helper manager. El primer push pedirá usuario y token.
  • VS Code como editor y herramienta de merge: git config --global core.editor "code --wait", git config --global merge.tool vscode, git config --global mergetool.vscode.cmd 'code --wait $MERGED'.

6. Crear y clonar repositorios

  • En GitHub (web): crear cuenta, crear repositorio, añadir un README y los ficheros del proyecto. GitHub Education ofrece ventajas a estudiantes.
  • Clonar: git clone URL crea una copia local con su carpeta oculta .git.
  • Iniciar uno nuevo en local: git init.
  • Clonar desde VS Code: Ctrl+Mayús+P o F1, escribir git clone y elegir la carpeta de destino.

7. Subir cambios (local → remoto)

  1. git status: ver qué ha cambiado.
  2. git add archivo, git add directorio o git add .: pasar al staging.
  3. git commit -m "mensaje": guardar en el repositorio local.
  4. git push origin main (o git push <remoto> <rama>): subir al remoto.
  • git add * no incluye los ficheros ocultos. git add . sí.
  • git push --force <remoto> <rama>: sube tus cambios aunque el remoto tenga otros. Puede borrar trabajo ajeno, así que es peligroso. Puede fallar si hay cambios remotos que no tienes en local.

8. Traer cambios (remoto → local)

  • git pull: descarga los cambios remotos y los fusiona.
  • git fetch / git fetch --all: descarga la información remota sin fusionar ni cambiar nada.
  • Ejemplo: cambias algo en la web de GitHub y luego haces git pull repoEntornosProfe main para traerlo a tu PC.

9. Repositorio remoto con nombre

  • git remote add nombre URL: guarda la URL con un nombre (por ejemplo origin).
  • git remote -v: lista los remotos configurados.

10. Deshacer cambios

ComandoQué hace
git restore --staged archivoSaca el fichero del staging area
git restore archivoRecupera lo borrado o modificado en el directorio de trabajo
git checkout -- archivoDescarta cambios y vuelve a la versión del repositorio. No borra historial
git rm archivoDeja de versionar el fichero. Con --cached lo mantiene en disco; con -r borra subdirectorios. Hay que hacer commit y push
git reset --softMueve la versión, sin tocar staging ni working directory
git reset --mixedToca el staging, no el working directory
git reset --hardElimina los cambios del staging y del working directory. Irreversible

Según los apuntes, reset borra el rastro en el historial, así que se usa con cuidado.

11. Conflictos y pull.rebase

  • Conflicto: dos personas modifican la misma línea del mismo fichero, o uno modifica un fichero y el otro lo borra.
  • Flujo de resolución:
    1. git pull (Git avisa de que hay cambios remotos).
    2. Abrir el fichero: verás las marcas <<<<<<<, ======= y >>>>>>>.
    3. Quitar las marcas y dejar el código final.
    4. Probar que el código funciona.
    5. git add ., luego git commit (o git rebase --continue si estás en rebase).
    6. git push.
  • Merge (por defecto): git pull crea un commit de unión.
  • git config --global pull.rebase true: Git aparta tus commits, descarga lo remoto y vuelve a poner tus commits encima. El historial queda en línea recta y sin commits de unión innecesarios.

12. Ramas

  • Qué es: una línea de trabajo independiente dentro del repositorio. Permite trabajar en paralelo.
  • Rama por defecto de GitHub: main.
  • git branch lista las locales (la actual lleva *). git branch -r: remotas. git branch -a: todas.
  • git branch nombre crea la rama, pero no te cambia a ella.
  • git switch nombre cambia de rama. git switch -c nombre (o git checkout -b nombre) la crea y te cambia a ella.
  • git push -u origin nombre sube una rama nueva y la vincula. Después basta con push y pull.
  • git branch -d nombre borra una rama local.
  • Traer la rama de un compañero: git fetch --all, luego git branch -r para verla y git switch nombreRamaCompi.
  • Fusionar: git switch main y git merge rama integra los cambios de la rama en main.
  • Flujo completo: git clone URL y cd repo, git switch -c feature, editar index.html, git add ., git commit -m "Cambio en feature", git switch main, git merge feature, git push.

13. Pull Request

  • Solicitud para integrar los cambios de una rama en otra, con revisión y aprobación antes de fusionar.
  • En GitLab se llama Merge Request.
  • Se crea desde la interfaz de GitHub o por comandos.
  • No se sube nada directo a la rama principal.

14. Versiones, etiquetas y nomenclatura

  • Tag: marca una versión concreta (por ejemplo 1.0.0). git push --tags sube las etiquetas.
  • Cambio mayor o release: cambio grande que genera una nueva versión del proyecto.
  • Cambio menor: añade funcionalidad sin romper lo anterior.
  • Bugfix o parche: arregla errores sin añadir funcionalidad.
  • Tarea beta: versión de prueba antes de la final.
  • Se puede crear una rama a partir de un tag para mantener una versión concreta.

15. Historial y estados

  • git log archivo y git show: historial de cambios.
  • git diff compara workspace y staging. git diff HEAD compara workspace y repositorio local.
  • Estados en VS Code: U (untracked, nuevo sin añadir), M (modificado), D (eliminado), T (tracked, bajo seguimiento), A (añadido al staging), R (renombrado), C (conflicto).
  • En los cambios de un fichero se distinguen las líneas añadidas, modificadas y eliminadas.

17. Puntos que suelen caer

  • Diferencia entre add y commit, y qué es el staging area.
  • Diferencia entre centralizado (SVN) y distribuido (Git).
  • Diferencia entre repositorio local y remoto, y entre push, pull y fetch.
  • Qué se hace en cada situación: clonar, traer cambios de la web, subir sin conflicto y subir con conflicto.
  • Diferencia entre restore, checkout y reset, y los tres modos de reset.
  • Qué es un conflicto y cómo se resuelve.
  • Qué hace pull.rebase y por qué deja el historial limpio.
  • Qué es una rama, cómo se crea y se fusiona, y qué es un Pull Request.
